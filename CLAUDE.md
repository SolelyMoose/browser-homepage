# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview
A static browser start page (daily to-do, homework tracker, one deadline countdown, time-based light/dark theme). Plain HTML/CSS/vanilla JS — no build step, no dependencies, no package.json, no test suite. The user sets `index.html` as their browser homepage via a `file:///` URL.

## Running / checking
- Open `index.html` directly in a browser.
- Browser automation tools can't open `file://` URLs; serve it instead: `python -m http.server 8765` from the repo root, then visit `http://localhost:8765/index.html`.
- Syntax check: `node --check app.js`.

## Architecture
- `app.js` is a single IIFE. State lives in three module-level variables (`todos`, `homework`, `deadline`), each mirrored to `localStorage` through the `load`/`save` helpers (both wrapped in try/catch). Storage keys: `hp.todos` (`{date, items}`), `hp.homework` (array), `hp.deadline` (`{label, due}` with `due` as ISO string).
- Rendering is full re-render: each mutation updates state, calls `save`, then `renderTodos()` / `renderHomework()` rebuild the list DOM. `makeItem()` is the shared list-row builder for both lists; `setProgress()` drives both progress bars.
- XP/levels: `hp.player` (`{xp, gems}`) stores total XP. The level is derived from it by `levelInfo()` and is never stored. `toggleDone(item, xp)` awards XP the first time an item is checked and sets `item.rewarded` so it can't be farmed. Gems are awarded in `gainXp()` for each level crossed (`gemsForLevel`). XP isn't part of export/import.
- Level-up effects: `levelUpFx()` first enlarges the header XP bar and tweens it to full (`chargeBar()`, `.player.charging`) while the screen rumbles (`body.rumbling`, `RUMBLE_MS`), then `releaseBar()` resets it and `playLevelUp()` plays the `#fx` overlay (shake via `body.shaking`, one SVG lightning bolt drawn by `lightning()` whose strokes CSS slowly widens, big `#lvl-pop` counter), then `burstGems()` flies gem sprites into `#gems` with the Web Animations API. The header shows `shownGems`, which catches up to `player.gems` as gems land. With `prefers-reduced-motion` it falls back to a toast. `previewLevelUp()` on `window` replays the effect without awarding anything.
- A single 1-second `tick()` loop updates the clock and deadline countdown; once per minute it also calls `applyTheme()`.
- Nothing auto-clears: to-dos and homework persist until the user deletes them (homework also has "Clear completed"). The user explicitly asked that daily to-dos never reset on their own. `hp.todos.date` is a leftover field and is no longer read.
- Theme: dark when hour ≥ 19 or < 7. The rule is duplicated in an inline `<script>` in `index.html` `<head>` (to avoid a flash before `app.js` loads) and in `applyTheme()` in `app.js` — keep both in sync. `applyTheme(hour)` is exposed on `window` so the theme can be forced from the console for testing.
- Export/import: `exportText()` / `parseText()` in `app.js` define a plain-text format for homework + deadline (documented in README). `parseText` returns `undefined` for a section missing from the text (leave as is) vs. `null` for `Deadline: none` (clear), and throws on an unreadable deadline date. If you change the export format, keep the parser accepting it so exported files round-trip.
- More section: the ⋯ button (`#more-toggle`) shows or hides `#more`. The open/closed state is stored in `hp.more` and handled in `app.js`.
- Math practice lives in `math.js`, a separate IIFE loaded after `app.js` with its own `load`/`save` copies. `TOPICS` is an array of `{id, group, name, gen}`. Each `gen()` returns `Q(text, fields, why, hint)`, and each field is an answer spec (`num`/`set`/`ineq`/`expr`/`primes`/`radical`/`sci`) checked by `CHECK[kind]`. Answers are parsed by a small expression parser (`clean` → `tokenize` → `parse` → `evalTree`), and polynomial answers are compared by evaluating them at sample x values. A checker throws `Retry` when the value is right but the form isn't (unsimplified, not factored, …), and that doesn't count as a miss. Storage: `hp.math` = `{needs: [{id, misses, streak}], mode}`. A topic leaves `needs` after `CLEAR_STREAK` correct answers in a row. Topic ids are stored, so renaming an id drops it from saved lists.
- Explanations: `why` stays one plain string. `whySteps()` in `math.js` cuts it into steps at display time (sentences, then clauses, then `=`/`≈` chains), only at spaces and never inside parentheses, so `steps.join(' ')` always equals the original. Write `why` text as normal sentences and it splits by itself. `whyPlayer(why, nextBtn)` builds the rows for both feedback boxes (Study gets it through `window.hpMath`) and reveals them on timers. All rows are in the DOM from the start so the box doesn't change size. With one step or `prefers-reduced-motion` it's a plain `<p class="m-why">`.
- Study lives in `study.js`, an IIFE loaded after `math.js`. It reuses that file's helpers and answer checking through `window.hpMath`, so it must load second. Its `TOPICS` are `{id, group, name, par, gen}`, where `par` is the goal time in seconds. Some `gen`s are borrowed from `math.js` topics with `reuse(id)`. The `word` answer spec (`{value, options, show}`, in `CHECK`) handles answers like `SAS` or `obtuse`, and anything outside `options` is a retry, not a miss. Storage: `hp.study` = `{off: [unticked ids], stats: {id: [{ok, ms}] newest first}}`, trimmed to the last `WINDOW` attempts. Storing `off` means new topics start ticked. Mastery is computed by `scoreAttempts()` and never stored, so changing the formula rescores saved attempts. Renaming an id loses its attempts. The timer (`syncClock`) only runs while a question is open, the tab is visible, and `#more` is open. `window.hpStudy` exposes `TOPICS`, `scoreAttempts`, `checkField`, `reviewTopics` and `assessTopics` for testing.
- Study modes: `startSession(mode)` takes `practice`, `review` or `assess`. Review and assess use a fixed `session.queue` chosen at the start (`reviewTopics()`, `assessTopics()`), and practice has a null queue and draws from the ticks live. Both orders use `byEase`, which treats `par` as difficulty, so changing a `par` changes the order. Review moves on after `REVIEW_STREAK` right in a row or `REVIEW_MAX` questions, and `session.moveOn` delays that until Next so the score text stays on the finished type. Assess skips the feedback box and `J.answer`, logs to `session.log`, and `showReport()` renders that into `#s-report`. The report is in memory only, but its attempts go into `hp.study` like any others.
- Effects live in `juice.js`, an IIFE loaded after `app.js` and before `math.js`, exposed as `window.hpJuice` (`J` in `math.js` and `study.js`). Sounds are synthesized with Web Audio in `SOUNDS` (no asset files) and played with `sfx(name, arg)`, which does nothing when muted (`hp.sfx`) or when the tab is hidden. Particles are drawn on one `canvas.juice` that is created on first use, and its frame loop stops when no particles are left. One-shot element animations use `anim()` (Web Animations) instead of CSS classes so they can restart while Enter is held. `math.js` and `study.js` only call scene functions (`question`, `answer`, `retry`, `flip`, `needs`, `meter`, …). Buttons in `#more` get a press animation and click sound from one delegated listener, and `OWN_SOUND` lists the ones that play their own. Streaks are per area (`m`/`s`), kept in memory only, and need `#m-combo` / `#s-combo`. With `prefers-reduced-motion`, `spawn()` and `anim()` do nothing and sounds still play. Effects must never delay input or the Study timer. `J.answer` updates the score through `showScore()` when the orbs land, on a timer because animation frames stop in a hidden tab. Sounds use `Math.random`, so they aren't deterministic.
- Styling: all colors are CSS variables on `:root`, overridden under `:root[data-theme="dark"]` in `styles.css`. The deadline card's color state (`none`/`ok`/`warn` <24h/`urgent` <3h/`past`) is set via `data-state` on `#countdown` and mapped to `--cd-color` in CSS.
